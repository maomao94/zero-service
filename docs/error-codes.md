# 错误码规范

本项目错误码参考大疆上云 `DJIErrorCode` 的 `ABCDEF` 六位设计，并与 gRPC 状态码、HTTP 网关信封解耦：

- **错误码**回答“业务上哪里错了”，跨语言、跨协议稳定；
- **gRPC Code / 语义 HTTP** 回答“错误属于哪一类”，用于分类与重试；
- **网关信封**回答“客户端怎么解析”，统一 `HTTP 200 + {code,msg,data}`，`code=0` 表示成功。

## 1. 设计原则

1. `0` 是唯一成功码，任何错误都不得使用 `0`。
2. v2 发布后数字码冻结，只允许追加，不允许重编号、复用或删除。
3. **BC 是产品功能域，不是技术分层**：参数、数据库、缓存、认证、外部依赖、网关等跨域错误统一放在 `00 通用`，不再单独占模块。
4. 一个功能域对应一组服务，错误码按域归属，不按“谁先实现”抢段。
5. 折叠类错误（内部错误、数据库、缓存、RPC）对外只返回统一文案，真实原因写日志；普通业务错误返回可展示的 `msg`。

## 2. 码位维度

错误码为 **ABCDEF** 六位数字：

```
  1 30 101
  │ │  └── DEF：模块内错误（三位）
  │ └───── BC ：功能模块（两位）
  └─────── A  ：错误来源（一位）
```

### 2.1 A：错误来源

| A | 含义 | 典型来源 |
| --- | --- | --- |
| `0` | 成功 | 仅 `000000` |
| `1` | 平台服务端 | 本仓库微服务、HTTP/gRPC 网关 |
| `2` | 客户端（预留） | Web / App / 第三方终端 |
| `3` | 设备 / 边缘端 | 机场、飞行器、IEC104、Modbus 现场设备 |
| `4` | 预留 | — |
| `5` | 云端 / 第三方平台 | DJI 上云、微信、OSS、LiveKit 云 |
| `6-9` | 预留 | — |

> 与 DJI 保持一致：`3` 表示设备端，`5` 表示云端/网关侧。本仓库服务端统一使用 `1`。
> 网关只放行 `extproto.proto` 中已登记的码，判据是枚举存在性、与来源位无关；未登记的设备/云端原始码不进入信封。

### 2.2 BC：功能模块

只对 `A=1`（平台服务端）的码生效，按产品能力划分。**当前已启用 2 个模块**：

| BC | 功能模块 | 归属/覆盖 |
| --- | --- | --- |
| `00` | 通用 | 跨域基础错误：参数、数据、缓存、认证、外部依赖、网关、未知/内部/超时 |
| `30` | 开放平台 | opengtw / facade/openapi：应用、密钥、method、限流 |

其他功能域（设备、会议、GIS、文件、AI、工业协议、容器、用户、第三方等）**按需申请，不提前预分配**；`90-99` 预留。

> `A=3/5` 的码来自 `dji_error_code.proto`，使用大疆自己的功能划分（例如 `312014` 的 `12` 表示设备升级），**不按本表解释 BC**；它们只出现在业务字段中，不占用 extproto 命名空间。

### 2.3 DEF：模块内错误

| DEF | 用途 |
| --- | --- |
| `100-899` | 模块内具体错误，按申请顺序递增 |
| `900-999` | 系统兜底与对外折叠（未知、内部、超时、系统繁忙） |

通用模块 `00` 内部再按 DEF 段细分，便于查找：

| DEF | 子域 |
| --- | --- |
| `100-199` | 参数/校验 |
| `200-299` | 数据/存储 |
| `300-399` | 缓存/消息 |
| `400-499` | 认证/授权 |
| `500-599` | 业务通用 |
| `600-699` | 外部依赖 |
| `700-799` | 预留 |
| `800-899` | 网关/传输 |
| `900-999` | 兜底/折叠 |

## 3. 命名规范

Go / proto 枚举名：`_<A>_<BC>_<SEMANTIC>`，语义使用大写下划线。

```proto
_1_30_APP_SECRET_INVALID = 130102 [(name) = "密钥无效", (http_code) = 401];
```

- 数字段必须与标识符一致，防止“名字写 01、号码是 30”的问题。
- 新增码必须同时提供中文 `name` 和语义 `http_code`。
- 修改文案可以，修改数字、语义 HTTP 必须走评审。

### 4.3 其他功能域

`10-25`、`40`、`50` 当前没有专属码，新增时按第 2.2 节归属追加，不跨域复用。

> 存量业务错误目前仍复用 `1005xx`（通用/业务）；新增错误或重构时按功能域落位，存量逐步迁移。这样既不打断现有服务，也避免把“参数/数据库”之类的技术分类再拆成模块。

> 语义 HTTP 仅用于分类、gRPC Code 推导和监控；网关实际响应见第 6 节。

## 5. gRPC 与错误码的映射

服务端返回错误时使用 `tool.NewErrorByPbCode`：

```go
return nil, tool.NewErrorByPbCode(extproto.Code__1_00_PARAM_INVALID, "会议标题不能为空")
```

- 六位码写入 gRPC `ErrorInfo.reason`；
- gRPC Code 由 `http_code` 推导；
- 调用方（网关）优先读取 `reason`，仅接受 extproto 中已定义的码；取不到时按 gRPC Code 兜底：

| gRPC Code | 兜底错误码 |
| --- | --- |
| `InvalidArgument` / `OutOfRange` | `100101` |
| `NotFound` | `100202` |
| `AlreadyExists` | `100203` |
| `Aborted` | `100204` |
| `Unauthenticated` | `100401` |
| `PermissionDenied` | `100402` |
| `FailedPrecondition` | `100502` |
| `ResourceExhausted` | `100701` |
| `Unavailable` | `100601` |
| `DeadlineExceeded` | `100997` |
| `Internal` / `Unknown` / `DataLoss` | `100998` |

网关对外前会做一次折叠：`100998`、`100201`、`1003xx`、`1006xx` 统一折叠为 `100999 系统繁忙`，真实原因只写日志。

### 5.1 设备/第三方原始错误码透传（DJI）

DJI 错误码是**独立枚举**（`third_party/dji_error_code.proto`），不翻译成 extproto，也不重新编号：

| 层 | 字段 | 规则 |
| --- | --- | --- |
| gRPC | `CommonRes.code` | DJI 命令结果：`0` 成功、`-1` 设备拒绝 |
| gRPC | `CommonRes.reason_code` | DJI 原始错误码，如 `312014`，原样返回 |
| HTTP 网关 | `data.reasonCode` | 原样透传，信封 `code` 仍为 `0`（调用成功，设备拒绝属于业务数据） |

```json
{
  "code": 0,
  "msg": "ok",
  "data": {"code": -1, "reasonCode": 312014, "message": "设备升级中，请勿重复操作"}
}
```

DJI 原始码**不进网关信封**。信封 `code` 只承载 extproto 中定义的平台码；设备执行结果一律通过业务字段返回。

Go 侧规则：

- 设备命令的拒绝结果由 `commandRes` 包装成 `CommonRes{Code: -1, ReasonCode: 312014}`，作为**正常响应**返回，不构造 error。
- 网关的 `PublicError` / `CodeFromStatus` 只认 extproto 中已登记的码；未登记的码进入网关错误路径时折叠为 `100999 系统繁忙`，原始值只写服务端日志。将来若把某个云端码正式纳入 extproto，它同样会被放行。
- 需要跨服务传递设备结果时，继续使用 `CommonRes.reasonCode`（或响应体 `data.reasonCode`），不要写入 `ErrorInfo.reason`。
- 第三方平台的**故障**（超时、连接失败、鉴权失败、限流、5xx）应在厂商包内映射成平台码（如 `100601`、`100602`、`100997`），再以 error 返回。

### 5.2 第三方错误转换（业务侧责任）

`extproto` 是唯一的错误码空间。其他系统的错误必须在业务/适配层完成转换——转换发生在调用厂商 SDK 的地方，不发生在网关。

| 厂商返回 | 处理 |
| --- | --- |
| 业务拒绝（设备拒绝执行、参数不合法等） | 转成业务字段（如 `CommonRes.reasonCode`），信封 `code` 保持 `0` |
| 平台故障（超时、连接失败、鉴权失败、限流、5xx） | 转成最接近的 extproto 码，以 error 返回 |
| 无法归类 | `100602 第三方服务异常`；连错误都拿不到时用 `100999` |

`msg` 可以承载人读的原始信息：

```go
return tool.NewErrorByPbCode(extproto.Code__1_00_THIRD_PARTY, "京东云鉴权失败（供应商码 401）")
```

约束：

1. `msg` 只给人看，客户端**不得解析** `msg` 做分支。
2. 不放凭据、URL、堆栈、完整厂商响应体；长度受控。
3. 机器需要的原始码走业务字段（`data.reasonCode`），不要塞进 `msg` 当协议。
4. 未在 extproto 登记的码一律降级 `100999`，原始值只进服务端日志。

## 6. 网关返回契约

适用于 `gtw`、`livegtw`、`opengtw` 等 HTTP 网关的业务路由。代码落地方式、鉴权出口与验收清单见 [`gateway-standard.md`](./gateway-standard.md)。

### 6.1 统一信封

```json
{"code": 0, "msg": "ok", "data": {}}
```

| 字段 | 说明 |
| --- | --- |
| `code` | 六位业务码；`0` 成功，非 `0` 失败 |
| `msg` | 可展示文案；成功固定 `ok` |
| `data` | 成功时的业务数据；失败时省略 |

### 6.2 HTTP 状态

**业务响应统一 HTTP 200**，包括鉴权失败、参数错误、下游错误。客户端必须以 `code == 0` 判断成功，不得以 HTTP 状态判断。

`X-Request-Id` 必须回显（缺失时由网关生成），排查问题时以该 ID 检索日志。

### 6.3 鉴权失败

| 场景 | 响应 |
| --- | --- |
| 缺少/错误 Basic 凭据 | `200 {"code":130102,"msg":"缺少或非法的 Basic 凭据"}` |
| JWT 缺失/过期/签名错误 | `200 {"code":100401,"msg":"未认证"}` |
| JWT 有效但缺少用户身份 | `200 {"code":100401,"msg":"缺少用户身份"}` |
| 应用不存在或已停用 | `200 {"code":130101,"msg":"应用不存在或已停用"}` |

### 6.4 网关自身错误

| 场景 | 响应 |
| --- | --- |
| 路由不存在 | `200 {"code":100801,"msg":"接口不存在"}` |
| 方法不允许 | `200 {"code":100802,"msg":"请求方法不允许"}` |
| 请求体超过上限 | `413`（go-zero 内置，空 body） |
| 请求超时 | `503` + 纯文本 `Request Timeout` |
| panic | `500`（go-zero 恢复中间件，空 body） |
| 反向代理不可达 | `502/504`（nginx 产生，非信封） |

业务路由内抛出的错误统一经 `gtwx.NormalizeError` 归一化：码必须存在于 `extproto` 枚举，否则降级为 `100999` 并记录日志。上表中由 go-zero 内置中间件直接写出的框架级错误不经过该函数。

### 6.5 明确例外

以下接口不适用统一信封，按协议语义返回状态码：

- `POST /webhook/livekit`：LiveKit 依赖 HTTP 状态决定是否重推，验签失败返回 `401`，业务处理失败返回 `500`。
- 微信支付/退款回调（`gtw/internal/handler/pay`）：成功响应由 PowerWeChat 按微信协议写出，不套业务信封。
- gRPC 直连：使用 gRPC status + `ErrorInfo.reason`，不使用 HTTP 信封。

## 7. 客户端处理建议

```java
// 伪代码
Response resp = http.post(...);
if (resp.code() != 0) {                 // 只认 code
    log.warn("requestId={} code={} msg={}", resp.requestId(), resp.code(), resp.msg());
    // 认证类：100401 / 130101 / 130102
    // 可重试：100999 / 100601
}
```

- 不要用 `HTTP 401` 触发重新登录，改用 `code == 100401 || code == 130101 || code == 130102`。
- 日志必须带 `X-Request-Id`。
- 未知 `code` 按失败处理，保留原始 `msg`。

## 8. 演进与兼容

1. **冻结数字**：`130101` 永远是应用不存在，即使文案调整。
2. **只追加**：新错误从对应功能域的空闲 DEF 递增；功能域用尽后申请新 BC 段。
3. **不复用**：删除的错误码保留占位，不分配给新语义。
4. **不跨域造码**：同一语义复用同一码；服务差异体现在 `msg` 和日志。
5. **标识符纠正**：只允许“数字不变、名称修正”。
6. **废弃流程**：文档标注 `deprecated`，至少保留两个发布周期。
